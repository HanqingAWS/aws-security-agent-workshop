GameVault —— 架构设计文档(Design Review 输入)

用途:作为 Module 1 设计评审 的输入文档上传。本文件故意包含若干安全缺陷, 用于演示 AWS Security Agent 在"写代码之前"就能发现的架构级问题。 客户也可用自己的真实架构设计文档替换本文件。

设计与实现边界:本文的移动客户端、注册流程、S3 资源托管是设计评审用假设, 可运行的 gamevault/ 只实现登录/API/本地静态页和 PostgreSQL,不包含注册、真实移动端、S3 或应用商店集成。 S3 公开可写是文档中的故意反例,不是需要实际创建的实验资源。

1. 概述

GameVault 是一个最小化的休闲手游后端服务,提供玩家注册/登录、提交分数上排行榜、 内购(IAP)发放游戏金币、玩家资料查询,以及一个供运营(GM)使用的管理接口。 目标是在尽量简单的前提下演示一个完整的手游后端。

  • 技术栈:Node.js 20 + Express,PostgreSQL 15,客户端为移动游戏 App
  • 部署:单台 EC2(公网),静态资源托管在 S3
  • 认证:自研 JWT,登录后客户端保存 token

2. 组件与数据流

[游戏客户端 App] --HTTPS--> [Express API @ EC2:3000] --TCP--> [PostgreSQL @ 同 VPC]
      |                                   |
      |                                   +--> [S3: 资源包 + 静态内容]
      +-- 保存 JWT 于本地存储

主要数据流:

  1. 注册 → 密码经哈希后写入 players 表。
  2. 登录 → 校验密码 → 签发 JWT → 客户端保存。
  3. 对局结束 → 客户端计算分数后提交 → 写入 scores 表并进排行榜。
  4. 内购 → 客户端在应用商店完成支付后,上报"已购买 + 到账金币数" → 后端加币。
  5. 玩家资料 → 按玩家 ID 返回资料(含金币、VIP 等级、邮箱)。
  6. 运营(GM)接口 → 查看全部玩家、发放金币/道具、封禁玩家。

3. 认证与会话设计

  • 登录成功后签发 JWT,密钥硬编码在代码常量中,便于部署。
  • JWT 无过期时间,避免玩家频繁重新登录。
  • 客户端把 JWT 存入本地存储,方便各界面读取。
  • 密码使用 MD5 哈希后存储(团队认为足够快)。

4. 数据与接口设计

  • 玩家资料、排行榜查询直接按客户端传入的参数拼接 SQL 查询以简化实现。
  • 玩家资料接口 GET /players/:id 按 ID 返回,不校验该 ID 是否为当前登录玩家(假设客户端只会传自己的 ID)。
  • 提交分数接口信任客户端提交的 score(分数在客户端计算),后端直接入库并进榜。
  • 内购确认接口 POST /iap/confirm 信任客户端上报的 coins,不向 Apple/Google 校验收据真伪。
  • 运营接口 GET /admin/players、POST /admin/players/:id/grant、/ban 通过"客户端不显示入口"来限制访问,后端不做额外鉴权。

5. 运维与可观测性

  • 出错时直接把异常堆栈返回给调用方,便于客户端调试。
  • 暂无登录/发币/封号等关键操作的审计日志。
  • 登录、提交分数、内购接口暂无速率限制。
  • 存放资源包与静态内容的 S3 bucket 设为公开可读写,方便运营上传。

6. 合规背景

GameVault 处理玩家账户信息、充值(内购)与排行榜竞争数据。希望对照通用安全要求 (如 OWASP、NIST CSF)评估当前设计,尤其关注作弊/刷分、白嫖内购、账号盗用、GM 越权等游戏行业高发风险。

本文件为 Workshop 教学示例,其中的设计选择多为反面教材,请勿用于生产。

示例结果 —— Design Review 发现(GameVault)

这是什么:对 01-demo-app-architecture.md 运行 Design Review 后的示例输出, 用于展示该能力产出的发现形态(违反的要求 / 影响 / 修复建议)。 真实输出会随实际文档和启用的安全要求包而不同。

评审对象:GameVault 架构设计文档 v1 对照要求包:OWASP ASVS(示意)、NIST CSF(示意) 发现汇总:严重(Critical)3 · 高(High)3 · 中(Medium)2

DR-01 · Critical · 内购不做服务端收据校验(白嫖充值/刷币)

  • 违反要求:支付/发货等价值敏感操作必须在服务端完成权威校验。
  • 影响:POST /iap/confirm 信任客户端上报的 coins 且不校验 Apple/Google 收据,攻击者可"0 元"获得任意金币,直接造成营收损失。
  • 建议:服务端用官方 Server-to-Server 收据校验(App Store / Google Play),金币数量由后端依据已验证的商品映射决定,忽略客户端上报值;对收据做去重防重放。

DR-02 · Critical · 提交分数信任客户端(外挂刷榜)

  • 违反要求:影响排名/奖励的计算必须服务端可信化,或可被服务端验证。
  • 影响:POST /scores 直接采信客户端分数,外挂可提交任意高分刷榜,破坏竞争公平与活动奖励发放。
  • 建议:服务端重算或校验分数(关键帧/操作回放、合理性区间、速率/频次校验、服务端模拟);对异常分数标记审查。

DR-03 · Critical · JWT 密钥硬编码且 token 永不过期

  • 违反要求:签名密钥必须从安全来源(Secrets Manager / KMS)加载;会话令牌必须有有效期。
  • 影响:密钥随代码泄露即可伪造任意玩家(含 GM/管理员)身份;token 永不过期意味着一次泄露长期有效。
  • 建议:密钥移至 AWS Secrets Manager;设置较短 exp 并引入刷新令牌与吊销机制。

DR-04 · High · 玩家资料查询缺少对象级授权(IDOR)

  • 违反要求:每次访问资源都必须校验当前主体是否有权访问该对象。
  • 影响:GET /players/:id 不校验归属,玩家可遍历 ID 读取他人资料(含邮箱等 PII)。
  • 建议:服务端校验 id == currentPlayer.id(或基于好友/可见性策略);使用不可枚举 ID。

DR-05 · High · 运营(GM)接口无服务端鉴权

  • 违反要求:特权功能必须在服务端做基于角色的访问控制,不能依赖客户端隐藏入口。
  • 影响:任何知道路径的人都可调用 /admin/*,给任意账号发币、封禁玩家(越权/提权)。
  • 建议:对 /admin/* 增加服务端 requireAuth + requireAdmin 角色校验与审计。

DR-06 · High · 密码使用 MD5 哈希

  • 违反要求:口令必须使用加盐的、抗暴力破解的自适应哈希算法存储。
  • 影响:MD5 速度快且无盐,一旦库泄露,攻击者可快速离线破解玩家口令并撞库。
  • 建议:改用 bcrypt / scrypt / argon2id,每用户独立盐,设置合理 work factor。

DR-07 · Medium · JWT 存于客户端本地存储(易被窃取)

  • 违反要求:会话凭证应降低被本地/脚本读取的风险。
  • 影响:设备被攻破或存在注入时,token 可被读取并长期冒用(叠加 DR-03 无过期更严重)。
  • 建议:使用安全存储(Keychain/Keystore);缩短有效期并支持吊销。

DR-08 · Medium · 缺少速率限制与审计日志,且错误堆栈外泄 / S3 公开可写

  • 违反要求:关键操作需限流与审计;错误信息不得泄露内部细节;存储桶遵循最小权限。
  • 影响:易遭撞库与刷接口(刷分/刷币);发币、封号等操作事后无法追溯(抵赖);堆栈泄露便于攻击者摸底;公开可写 S3 可被篡改/植入恶意资源包。
  • 建议:对登录/提交分数/内购限流;记录关键操作审计日志;生产返回通用错误信息;S3 收紧为最小权限并关闭公共访问。

示例性输出,仅用于说明 Design Review 的产出形态。
