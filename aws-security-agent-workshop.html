AWS Security Agent 动手 Workshop › 概览

AWS Security Agent (AWS Continuum) 动手 Workshop

面向有一定 AWS 基础的进阶客户（开发 / 安全 / 架构角色），通过动手操作一个贯穿 SDLC 的示例应用，直观理解该服务的四大能力与价值。

课前须知 · 2026-10-15 核对核心课堂约 2.5–3 小时，不含课前搭建、可选模块和异步等待。准备已完成的获授权预跑报告，不能保证现场扫描及时完成或检出全部预设漏洞。本页为社区教材，所有结果示意均不是实际服务运行证据。
⏱ 总时长 约 2.5–3 小时 👥 形式 讲师引导 + 动手 🎯 示例应用 GameVault（手游后端）

学习目标

理解定位把安全"左移"：在设计、编码、部署各阶段持续、自动地发现并验证风险。
动手四大能力亲手完成 设计评审 → 威胁建模 → 代码评审 → 渗透测试 的闭环。
看懂输出读懂每种能力的发现结果：严重度、证据、攻击链、修复建议。
联系场景把能力映射到真实研发流程与游戏行业典型风险（外挂、刷币、越权）。

1 · 服务简介

AWS Security Agent（现已归入 AWS Continuum） 是一个贯穿软件开发生命周期（SDLC）的前沿 security agent，帮助团队把安全"左移"并持续验证：从设计到部署，自动发现并验证漏洞。

🧩 设计评审 Design Review
写代码之前，评审架构设计文档是否符合组织安全要求。
🕸 威胁建模 Threat Modeling
基于设计文档/源码，自动生成系统架构理解 + STRIDE 威胁清单。
🔍 代码评审 Code Review
对完整代码库和 Pull Request 做静态分析，检测漏洞并校验合规。
💥 渗透测试 Penetration Testing
对已部署应用自主执行多步攻击链，发现并验证可利用漏洞。
核心价值主张把传统上周期性、昂贵、依赖专家的安全活动（尤其是渗透测试），变成随时可触发、可规模化的自动化能力；并且给出的是已验证的可利用性，而非仅理论 CVSS 评分。

三个工作界面 / 三种角色

角色工作界面在 Workshop 中对应
Administrator（管理员）AWS Management Console讲师 / 环境搭建者
User（用户）Security Agent Web Application所有动手参与者
Developer（开发者）GitHub / IDE（如 Kiro、Claude Code）可选进阶模块

同一个人可同时拥有三种角色。Workshop 中通常由讲师用 Administrator 搭好环境，再把 User 权限分配给学员。

关键概念 · Agent Space每个 Agent Space 是针对一个应用的隔离工作区，保存该应用的设计评审、威胁模型、代码评审配置、渗透测试目标与发现结果。一个应用建一个 Agent Space。而"安全要求包（security requirement packs）"是账户级全局定义、对所有 Agent Space 生效。

2 · 示例应用：GameVault（手游后端）

GameVault 是一个最小化的休闲手游后端：玩家登录、提交分数上排行榜、内购发放金币、玩家资料查询，以及一个供运营（GM）使用的管理接口。它故意植入一组一致的缺陷，贴合游戏行业典型风险（外挂刷分、白嫖内购、GM 越权、账号盗用），完整可运行代码见 workshop-materials/gamevault/。

核心接口

POST /login 登录，返回 JWT GET /players/:id 玩家资料（需登录） POST /scores 提交分数上榜（需登录） GET /leaderboard/search 排行榜搜索（公开） POST /iap/confirm 内购确认发币（需登录） GET /admin/players GM：列出所有玩家 POST /admin/players/:id/grant GM：发放金币 POST /admin/players/:id/ban GM：封禁玩家

贯穿全程的"故意缺陷"追踪表

这组缺陷被设计成跨阶段可追踪——同一个问题会在不同能力中层层递进地出现，这是本 workshop 最有说服力的叙事主线。

客户端提交分数被信任外挂刷榜✅✅ Tampering✅✅ 刷榜首
内购不校验收据白嫖充值/刷币✅✅ Tampering✅✅ 0 元得币
GM 接口无鉴权任意发币/封号✅✅ Elevation✅✅ 提权
SQL 注入（拼接）拖库/绕过—✅ Tampering/Info✅✅ 拖库
IDOR 越权读资料他人账号/PII✅✅ Info Disclosure✅✅
JWT 密钥硬编码/弱伪造玩家/管理员✅✅ Spoofing✅✅ 伪造 token
密码用 MD5撞库破解✅✅ Spoofing✅—
反射型 XSS排行榜搜索注入—✅ Tampering✅✅
无速率限制撞库/刷接口✅✅ DoS——

⚠️ 仅供教学GameVault 含真实可利用漏洞，切勿用于生产，且只对你拥有授权的目标做测试。种子账号：alice / password1（玩家）、admin / admin123（管理员）。

3 · 环境准备（讲师在 Workshop 前完成）

目标学员到场后能直接进入动手模块。本节由讲师提前完成。

3.1 账户与权限

  • 建议使用专用 workshop 账户（渗透测试会产生需隔离的发现结果）。
  • 搭建身份与学员运行身份分开，学员不分配管理员权限或 securityagent:*。按官方角色说明审核控制台生成的角色，权限限定到所选实验资源。CloudWatch Logs 动作为 logs:CreateLogGroup，不是 cloudwatch:CreateLogGroup。
  • 仅上传虚构数据；客户源码、设计和日志先完成分类及上传授权。设置日志/S3 保留期限，GitHub App 仅授权所需实验仓库。
  • 服务可用区域会持续变化，以 AWS 官方控制台实际可选区域为准。

3.2 两个 IAM Service Role（控制台自动创建）

角色范围作用
Application role每个应用一个允许 Web App 调用 Security Agent API，使用官方托管策略和受限服务信任关系。
Agent Space service role每个 Agent Space 一个允许访问挂载的 AWS 资源（VPC、S3、Secrets Manager、CloudWatch、Lambda）。

3.3 用户访问：SSO vs IAM-only

方式适用要点
IAM Identity Center (SSO)多人 Workshop（推荐）学员无需 Console 凭证即可登录 Web App；会话最长约 12 小时。
IAM-only access单人演示 / Demo有 Console 访问者通过 "Admin access" 进入；会话约 30 分钟过期。

3.4 GitHub 集成（讲师提前装好）

  1. 创建 registrationConsole → Agent Space → Integrations → Add → Create new registration → 选 GitHub。
  2. 安装并授权点 Install and authorize → 跳转 GitHub → 选择 org/user 和仓库 → Install & Authorize。
  3. 命名复用回到 Console 为 registration 命名并确认账户类型。该 registration 可跨多个 Agent Space 复用。
公开教材与私有实验仓库分开公开仓库可只读分析，不支持 Code review comments / Code remediation 写操作。将教材源码复制到专用私有实验仓库（不是公开 fork），每组独立命名；安装 App 时只选该仓库并授予所需读写权限。一个仓库的写操作只能由一个 AWS 账户启用。官方限制。

提前完成登录、仓库集成与目标验证并预跑。默认仅由讲师启动一次共享渗透测试，避免学员重复计费；明确预算、停止责任人和清理责任人。本实验不启用定时任务。

Module 0 · 环境搭建

⏱ 约 30 min👤 Administrator讲师演示，学员观摩
A功能介绍

Security Agent 的配置分两处：Console（搭建 Agent Space、定义安全要求、连接资源、管理用户）与 Web App（运行各项评估）。本模块让学员建立这个"配置 / 操作"分工的认知。

B操作步骤
  1. 进入服务AWS Management Console → AWS Security Agent → Set up AWS Security Agent。
  2. 创建 Agent Space填名称 workshop-gamevault 与描述（该名称会显示给 Web App 用户）。
  3. 选择访问方式User access configuration 选 IAM Identity Center（多人）或 IAM-only access（单人）。
  4. 完成创建点 Set up AWS Security Agent → 控制台自动创建 Agent Space、application role 和 Web App URL。
  5. 分配学员进入 Agent Space → Web app 页签 → Assign users 加入每位学员，并把 Web App URL 发给他们。

Module 1 · 设计评审 Design Review

⏱ 20–25 min👤 User
A功能介绍

在写任何代码之前，上传架构设计文档，Security Agent 对照组织安全要求（如 OWASP ASVS、NIST CSF）评审设计，指出架构级缺陷与具体改进建议——这是最彻底的"安全左移"。

B功能定位与应用场景
定位：SDLC 最前端的"设计关卡"。
典型场景：新功能立项评审、架构变更评审、安全基线自查；在方案阶段就拦住"把 token 存错地方""内购不校验收据"这类昂贵的结构性错误，避免返工。
C操作步骤
  1. 准备文档用配套 workshop-materials/01-demo-app-architecture.md（GameVault 架构文档，含故意缺陷），或替换成客户自己的设计文档。
  2. 新建评审登录 Web App → 选 Agent Space → Design Review → New design review，上传文档（PDF/Markdown）。
  3. 选要求包（可选）启用 AWS-managed 安全要求包（如 NIST CSF）或自定义要求。
  4. 运行点 Run，约 5 分钟。
  5. 查看发现每条发现含：被违反的要求、影响、具体修复建议。

Module 2 · 威胁建模 Threat Modeling

⏱ 30–35 min👤 User
A功能介绍

基于设计文档（scope doc）和/或源码，自动生成系统概览（组件、信任边界、数据流）和一份按 STRIDE 分类、带严重度与缓解建议的威胁清单。

B功能定位与应用场景
定位：把"专家主导、耗时数天"的威胁建模变成分钟级、可重复的自动产物。
典型场景：新特性设计阶段系统化识别攻击面；安全评审会前快速产出 STRIDE 基线；为渗透测试圈定高风险重点。
C操作步骤
  1. 连接源码Console → Agent Space → Threat modeling 页签 → 连接 GitHub 仓库（或含源码的 S3）。
  2. 新建模型Web App → Threat Models → Create threat model，填 Title。
  3. 提供输入至少一种：Scope docs（上传 03-threat-model-scope-doc.md 聚焦"内购+排行榜"）和/或 Sources（选已连接仓库）。两者同时提供效果最好。
  4. 运行选 Service role → Create → Start run（约 5–10 分钟）。
  5. 查看结果Overview 看系统概览与严重度分布；Threats 看每条威胁的 STRIDE 分类、严重度、缓解建议，可标记 Resolved / Dismissed。

Module 3 · 自动化代码评审 Code Review

⏱ 35–40 min👤 User + Developer
A功能介绍

对源码做静态分析，检测漏洞并校验组织安全要求。两种模式：全仓库扫描（Web App 发起）与 PR 级自动扫描（在 GitHub Pull Request 评论里直接给出发现，并可自动开修复 PR）。

B功能定位与应用场景
定位：嵌入开发工作流的持续代码安全闸门，兼顾"存量全扫"与"增量 PR 守门"。
典型场景：遗留系统安全体检、每个 PR 的自动安全评审、把修复建议直接变成可合并的 PR，缩短"发现→修复"闭环。
C操作步骤

Part A · 全仓库扫描（Web App）

  1. 新建评审Web App → Code Reviews → Create code review，Title 如 gamevault-security-review。
  2. 选源与设置Sources 选已连接的 GitHub 仓库；默认 Security requirements and vulnerability findings（查漏洞 + 合规）。
  3. 运行选 Service role → Create → Start review（约 30–60 分钟，视代码量）。
  4. 查看与修复每条发现含严重度、受影响文件/行号、Suggested fix；私有实验仓库启用写权限后点 Remediate code 请求修复 PR。公开教材仓库只解读建议。

Part B · PR 级自动扫描（GitHub）

  1. 开启 PR 评论Console → Agent Space → Code review → 为仓库开启 Code review comments（及可选 Automatic remediation）。
  2. 制造改动在已集成的私有实验仓库创建分支，加一处故意改动，提交同仓 PR；不要向公开教材发漏洞练习 PR。
  3. 看自动评论核对触发条件、权限和配额，等待发现与修复建议；不保证几分钟完成。修复 PR 需人工审查再合并。

Module 4 · 按需渗透测试 Penetration Testing

⏱ 约 40 min👤 Administrator + User
A功能介绍

对已部署的应用自主执行多步攻击链，发现并验证可利用漏洞——给出的是真实的、可复现的利用证据，而非理论评分。这是本服务区别于静态分析最有冲击力的能力。

B功能定位与应用场景
定位：把一年一两次、昂贵的人工渗透测试，变成随时可触发、可规模化覆盖整个应用组合的能力。
典型场景：上线前的部署验证、重大变更后的回归测试、把渗透测试扩展到以往"测不起"的长尾应用。
讲师预备（Workshop 前）优先使用隔离的私有 VPC 目标，配置目标 VPC、可达子网、执行器安全组和 Private VPC 验证。完整域名需与验证域名匹配。公网目标仅作获批备选，限制测试流量来源；仅放行学员 IP 不代表服务可达。见 gamevault/DEPLOY.md，提前完成验证与预跑。
C操作步骤
  1. 配置日志/凭证Console → Agent Space → Penetration test → 配置 CloudWatch 日志组（可选 Secrets Manager 凭证做登录态测试）。
  2. 新建测试Web App → Penetration tests → Create a penetration test，填名称；Target URLs 选已验证域名 → Save & Next。
  3. 范围与上下文（可选）配置 VPC / 凭证 / 网络范围分类（把每个可触达域名标为 Accessible 或 Out of scope）；附加源码/文档上下文、开启自动修复。
  4. 执行与预算设置 Max task hours（当前最小 20，不默认 No limit）后点 Create and execute。Preflight 校验可达性；整体可能数小时，课堂优先解读已完成的预跑报告。
  5. 查看发现Run overview / Logs / Findings：每条含攻击链、利用证据、影响分析、可落地的代码修复。
  6. 修复并复验私有仓库启用写权限后点 Request remediation 请求修复 PR；人工审查、合并并重新部署后复验。复验为独立任务，不自动改写原始发现状态。
💡 重点讲解task-hours ≠ wall-clock（墙钟时间）。并行 agent 任务意味着计费累积比测试时长更快——一次 30 分钟的测试可能消耗数个 task-hour。

5 · 常见坑与讲师提示

搭建类

  • 域名验证有延迟：DNS TXT 验证可能 10–30 分钟，务必提前一天完成。
  • 没启用 SSO 很痛：IAM-only 时学员每次登录都需 Console，且 admin-access 会话 30 分钟过期，演示中途掉线很尴尬。
  • 私有端点需配 VPC：推荐隔离私有目标，提前核对 DNS、网络、TLS 和权限；不要为省事公开漏洞应用。
  • 范围的路径继承：父路径被排除则嵌套子路径自动排除；不支持通配符/正则，需显式规划 in-scope 路径。
  • GitHub App 权限：提前把 App 装到 workshop org 仓库；学员在个人仓库授权会遇到 org 策略限制。

节奏类

  • Module 3/4 有较长异步等待：在 Module 4 开头就把渗透测试跑起来，等待期间讲代码评审或讨论。
  • 可预先跑好一个完成的渗透测试，时间紧时直接展示"已出结果"视图。
  • 坚持用同一个应用跑 Module 1→4，让学员看到发现跨 SDLC 的演进。

成本类

  • 代码/设计评审、威胁建模在当前 Preview 阶段不收服务费，但配额和 EC2/S3/日志等配套费用仍需核对。
  • 渗透测试当前公开价 $50/task-hour，按秒累计。Max task hours 最小 20，对应最高 $1,000 服务费，不是必花金额；试用、折扣和税费另计。少量 URL 或短墙钟时间不保证低费用。
  • 服务配额与预算告警不是硬性停止开关。明确所有运行的累计预算；预算不足时使用预跑报告，不发起真实测试。
  • 实际价格与免费额度以 AWS 官网为准。

6 · 总结与后续

回顾：一条缺陷贯穿四大能力

以"硬编码/弱 JWT 密钥"为例，看它如何沿 SDLC 层层被发现——这正是本 workshop 想让客户记住的主线：

设计评审 DR-03 ──► 威胁建模 TM-03 ──► 代码评审 CR-03 ──► 渗透测试 PT-02 （指出密钥硬编码） （标为 Spoofing 威胁） （定位到具体代码行） （伪造管理员 token 实证提权）
一句话价值Security Agent 让安全在设计、编码、运行时每个阶段都在场，并把最昂贵的渗透测试变成随时可用、给出已验证可利用性的能力。

建议的后续行动

🧪 发起 POC
用客户自己的一个真实应用，重复本 workshop 的四步流程。
📏 定义安全要求包
把客户组织的安全标准沉淀为 requirement pack，让评审贴合自身合规。
🔗 接入 CI/CD
在 PR 流程中默认开启代码评审评论与自动修复。
📝 收集反馈
现场收集最打动客户的能力与顾虑，指导后续跟进。

验收与课后清理

  • 每个模块记录实际运行 ID/状态，解释至少一条发现的证据、业务影响和缓解建议；指出一条信任边界和两类 STRIDE 威胁。样例不当作真实扫描证据。
  • 停止运行/定时任务，核对费用；只清理本实验的容器、数据库卷、EC2/ALB/EIP/DNS、源码副本和凭证。
  • 按组织策略保留/删除报告与日志，撤销专用仓库授权。自动修复先审查、部署，再复验；不代表生产安全保证。
